## 捨てた選択肢と理由

- **色パラメータの CLI 引数化 / 設定ファイル化**: 初回検証では不要と判断。結果を見てから可変化を検討する方針。今回の結果を見ても camSony1_L では十分機能しており、当面固定のままで問題なし
- **新規可視化スクリプト作成**: feat-033 のスコープ外とした。既存 `visualize_tracking.py` の `--id-field` 追加による流用可能性も、本案件では検討対象外に含めた
- **pink_id をトラッカー ID として使う（1フレーム内で複数人に割り当て可能な形）**: feat-033 時点では「1フレーム最大1人」の単純方式を採用。複数人追跡は feat-034 で Deep OC-SORT と組み合わせて解決する
- **`load_data()` の流用（キーポイントを numpy 化）**: `postprocess_reid.py` の既存ローダーを流用せず、JSON の生 dict を保持する方式を採用。理由は ADR-001 に記録（pink_id 付与ではキーポイント numpy 化が不要、生 dict 保持の方が `stable_id` など将来フィールドを自動保持できる）
- **プレースホルダ `(0,0,0,0)` で bbox 欠損を埋める**: レビュー指摘（M-2）を受けて `None` 詰めに変更。`select_pink_bbox` 内で `ratio=0.0 < 閾値` により自動除外される
- **元BBを整数化せず float のまま `prev_selected_bbox` に保持**: 却下。参考元 `pink_tracker_jhub.py` L114-117 がクリッピング後整数BBを `last_box` に格納する挙動と一致させるため、ADR-003 でクリッピング後整数タプルを採用
- **feat-032 をこのまま進める**: 却下。feat-033 の結果で「ポーズ誘導外観特徴量の汚染を観測して修正する」動機が薄れ、色ベース方式に全面移行する方が実用的と判断
- **bug-XXX ケースを今セッションで作成**: 却下。ユーザーがバグ詳細を次セッションで提示し、正規フロー（ステップ1から）で着手する方針

## 学び

- **色ベース選択はポーズ誘導 HSV ヒストグラム + EMA より汚染に強い**: 時間平滑化（EMA）が汚染源になる設計は避けるべき。各フレーム独立計算 + IoU 連続性ボーナスで「時間的一貫性」を出す方式の方が、汚染リスクを避けつつ安定追跡できる
- **stable_id 断片化の深刻さ**: camSony1_L で 444 個のユニーク ID に患者が分散していた。feat-026 で観測された「42分途切れ」は氷山の一角であり、広範な ID スイッチ + EMA 汚染が常時発生していた
- **BB 重複除去（feat-025 案A）の限界**: キーポイント類似度で重複判定しているため、画面際のキーポイントが暴れる位置では機能しない（ユーザー指摘）。feat-033 の19複数検出フレームはこの既知限界の結果
- **`postprocess_reid.py` の `load_data()` はタスク依存**: キーポイントを numpy 化する処理は Re-ID でしか使わない。pink_id のような純ポストプロセスでは生 dict 保持の方が汎用性が高い
- **`pink_tracker_jhub.py` 由来のロジックはポータブル**: ROI切り出し + HSVマスク + IoU連続性ボーナスだけで、YOLO形式でも OpenPose JSON 形式でもほぼそのまま流用できた
- **レビューループは2ラウンドで収束した**: Round 1 で 4高・4中、Round 2 で 0高・2中、Round 3 不要。反復的に品質を上げる仕組みは有効だが、Round 1 で質の高い指摘を引き出すにはレビュー対象を増やしすぎない（README + requirements + design の3点セットに絞る）ことが鍵
