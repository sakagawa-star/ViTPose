## 決定事項

- **ROI 方式**: (II-a) 軸並行最小矩形を採用。(I) 多角形・(II-b) 回転矩形は不採用（キーポイント精度依存・縮退リスク）
- **K-2 方式採用**: 信頼できる点（conf≥0.3）の座標のみで min/max 矩形構築。K-1（4 点全座標使用）は低信頼点 (0,0) によるROI 暴走リスクで却下
- **F2 厳しめ採用**: ROI 構築不能なら pink_ratio=0。F1（BB 自動フォールバック）は比較純度を損なうため却下
- **ハイブリッド構造（feat-046 ADR）**: 色は ROI ベース（`pink_ratio`）、IoU 連続性は人物 BB ベース（`iou_with_prev` / `prev_selected_bbox`）。`select_pink_bbox` のシグネチャ・ロジックは不変
- **既存 `clip_bbox` の再利用**: `build_keypoint_rect_roi` の丸め・クランプは既存 `clip_bbox(...)` を呼ぶ DRY 設計
- **CLI 引数（feat-046）**: `--roi-mode {bb,keypoint-rect}` (default bb), `--kpt-conf-min 0.3`, `--min-roi-area 200`
- **bb モード後方互換**: bb モードでは新規フィールド `roi_mode` / `roi_bbox` を書き込まず、出力 JSON は改修前と完全一致（AC-003-1 は `diff -r` で検証）
- **feat-047 スクリプト 2 分割**:
  - `compare_roi_modes.py` (α-1 散布図 PNG + 不一致 CSV)
  - `visualize_disagreement_frames.py` (PNG 静止画、bb=赤/kp=青、float→int 変換、黒縁取り白文字)
- **CSV bbox 小数 2 桁丸め**: 可読性 + 再パース安定性のため `round(v, 2)` で書き出し
- **CSV パース例外**: `ast.literal_eval` 失敗時は WARNING 出力で当該 bbox を None 扱いに、クラッシュさせない
- **CSV 4 タイプ分類**: `both_selected_different` / `only_bb` / `only_kp` / `both_none`（`both_none` は一致扱いで CSV 除外）

## 捨てた選択肢と理由

- **(I) 多角形 ROI**: 4 点の順序が崩れると自己交差で蝶結び形状になり ROI 無意味化、上限性能の参考としては有用だが実運用には不向き
- **(II-b) 回転矩形 ROI**: `cv2.minAreaRect` が低信頼点に引っ張られて回転角度が不安定
- **K-1 方式（4 点全座標使用）**: 未検出点が (0, 0) で出力されるため min/max 矩形が画像左上まで暴走
- **F1 フォールバック（BB 自動フォールバック）**: 「成功すれば keypoint、失敗すれば BB」のハイブリッドとなり純粋比較不能
- **GT-2（pink_track_id 擬似正解）**: 検証時に擬似正解を立てる案は循環参照リスク。代わりに不一致フレームを目視判定する方式を採用
- **同一 BB 紫描画**: 不一致 CSV から除外されるため visualize 入力に到達せず、設計簡素化のため削除
- **IoU 連続性も ROI ベース化**: 色変更と IoU 変更が合算され効果分離不能、bb モードとの差分純度が崩れるため却下
- **キーポイント ROI を含む 3 モード以上の同時比較**: scope 拡大、2 モード比較に絞る
- **動画形式の比較出力（V-1 / V-3）**: 数千件の不一致になるとビュー負荷が高い、静止画 V-2 を採用
- **HSV 範囲・閾値の CLI 化（feat-044 凍結時の検討）**: feat-046 はキーポイント関連 CLI のみ追加。HSV 範囲変更は本スコープ外
- **feat-046 と feat-047 を 1 案件で合体**: 「シンプルな機能を一つずつ作る」CLAUDE.md 方針に反するため分離

## ハマりどころ

- **既存コードの clip_bbox 仕様確認漏れ**: 初期 design.md で `width-1` / `width` のクランプを誤って混在 → 既存実装は両端 `width-1` / `height-1` で統一されており、Bash で `grep` 確認して修正
- **bbox 型が float の list**: cv2.rectangle は int 要求のため `tuple(int(round(v)) for v in bbox)` 変換が必須。レビューで指摘されて修正
- **HALPE26 番号の独自勘違い**: 一時的に番号定義の不整合を疑ったが、CLAUDE.md と一致を確認して問題なし
- **不一致 CSV の bbox 同値比較（float の `==`）**: 丸め誤差で偽陰性リスクあり → bb_index ベース判定に切替、紫描画自体を廃止
- **ハイブリッド構造（色=ROI / 連続性=BB）の意味論未定義**: H-3 レビュー指摘で発覚。`prev_selected_bbox` に「BB を入れるか ROI を入れるか」の判断が明示されていなかった → ADR を追加して人物 BB を維持と明記
- **設計判断 ADR の重複セクション**: 修正の過程で §4.4.2 ADR と §4.4.4 ADR が重複生成 → §4.4.5 を「廃止」スタブにしたが、低指摘で残置（実害なし）

## 学び

- **アイデア出しを段階的に進める価値**: Phase 1（課題言語化）→ 発散 → 制約確認 → 案件分割、の構造で論点抜けを防ぐ。今回も α/β/γ/δ 指標の選定、不一致 4 タイプ、サンプリング規約、CLI 設計を段階的に詰められた
- **「擬似正解の循環参照」の罠を避ける**: 既存 pink_id=1 を正解として keypoint-rect を評価すると自己回帰になる。**不一致フレームのみを目視判定**する設計は循環参照を避ける良い手段
- **K-1 / K-2 のような実装方式の選択は座標値の境界挙動から考える**: 未検出 keypoint が (0, 0) で返る性質を知らないと K-1 を選んでしまう。HALPE26 推論結果の実例確認が重要
- **bbox 同値比較は ID 系で行う**: float 座標を `==` 比較するのは丸め誤差で危険。`bb_index` のような ID 比較が安全
- **clip_bbox の再利用は DRY だけでなく仕様整合性も保証**: 同じ丸め基準を独立に再実装するとレビューで「不一致」指摘が出る。既存純関数を呼べば自動的に整合
- **F2 厳しめは比較の純度を保つ**: 自動フォールバックを入れると「効果」と「フォールバック頻度」が混ざる。本案件は比較が目的なので F2 が適切
- **ハイブリッド設計の明示**: 色は ROI、連続性は BB、というように軸ごとに方式を分ける場合、ADR で意図と却下案を明記しないと実装者が誤解する
