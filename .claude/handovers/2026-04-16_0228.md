## 決定事項

### パイプライン構成（β採用）

4ステージの単一責任構成。各ステージが独立した中間 JSON を出力するため、切り分けが容易:

```
Stage 1: run_halpe26_pipeline_yolo11.py（既存、feat-012/024）
         → JSON (bbox, keypoints, bbox_score)
Stage 2: postprocess_track.py（新規、feat-035）
         → JSON + track_id（Deep OC-SORT 単独、custom_reid.py を使わない）
Stage 3: postprocess_pink_id.py（既存、feat-033、修正不要）
         → JSON + pink_id（track_id は通過）
Stage 4: postprocess_pink_track_id.py（新規、feat-036）
         → JSON + pink_track_id（動画不要、JSON のみで完結）
```

### ハイブリッドトラッキングの基本戦略（feat-036 で実装）

- **服が見える区間**: `pink_id=1` の BB の `track_id` を「現在の患者 track_id」として記憶
- **服が見えない区間**: 記憶した patient track_id を持つ BB に `pink_track_id=1` を付与し追跡を延長
- **patient track 消失時**: 次に `pink_id=1` が観測されるまで `pink_track_id=-1`
- **新しい pink_id=1 観測時**: その BB の track_id を新しい patient track_id として更新
- 狙い: 「腕だけ見える → 服も見える → 布団で隠れる → 再び見える」という状況でも追跡継続

## 学び

- **単一責任原則 × 切り分け容易性**: パイプラインを分けることで各ステージの中間 JSON が証拠になり、問題発生時に原因を段階的に局所化できる。開発・デバッグのコストよりも中間ディレクトリの増加コスト（camSony1_L で約 5 GB）の方がはるかに小さい
- **既存資産の ADR を読む価値**: feat-033 の ADR-001 に明記された「生 dict 保持設計」のおかげで、Stage 3 の再実装を避けられた。設計書の ADR は将来の判断の根拠になる
- **Deep OC-SORT の 1 方向処理**: オンライントラッカーは 2 パス処理を前提としない。結合ロジックの設計時にこの前提を明確にしておくことで、設計の選択肢を絞り込める
- **ロードマップ案件（meta 案件）の有効性**: feat-019 と同じパターンで feat-034 を meta 化することで、「全体設計の合意形成」と「個別実装」を分離できた。議論フェーズが長くなる時は meta 案件を先に立てるべき
- **レビューループ方式**: 前回 feat-033 でも Round 2 で収束。今回も Round 1 で 3 件 → Round 2 で 0 件と 2 ラウンドで収束。反復方式は有効
