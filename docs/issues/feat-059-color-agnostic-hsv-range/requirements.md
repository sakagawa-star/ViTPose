# feat-059 要求仕様書: analyze_clothing_color.py の色非依存レンジ提案

## 1. プロジェクト概要

- **何を作るのか**: `scripts/analyze_clothing_color.py` を改修し、入力された服の静止画が有彩色でも無彩色（白・黒・灰）でも、その服の色を捕まえる HSV レンジ（`postprocess_pink_id.py --hsv-config` 互換 JSON）を提案できるようにする。
- **なぜ作るのか**: 現状は有彩色専用で、白い服（例: E0049 患者）を入力しても患者を追跡できる特徴量（レンジ）を出せない。色に依存せずレンジを提案できれば、白・黒系の服の患者にも色ベース同定（`postprocess_pink_id.py`）を適用できる。
- **誰が使うのか**: 本リポジトリで患者同定パイプラインを運用する開発者（ユーザー本人）。
- **どこで使うのか**: Linux / Python 3.10 / uv 環境。GPU（cuda:0）で ViTPose 推論を行う既存ツールの実行環境。

## 2. 用語定義

機能設計書・コード内でも本節の用語を使用する。

- **服色レンジ**: 服の色を `cv2.inRange` で抽出するための HSV 下限・上限ペアのリスト。`postprocess_pink_id.py` の `FIXED_HSV_RANGES` および `--hsv-config` の `fixed_hsv_ranges` と同形式。形式は `[((H_lo,S_lo,V_lo),(H_hi,S_hi,V_hi)), ...]`（色相環またぎ時は2レンジ）。
- **胴体ROI**: HALPE26 の胴体4点（左右肩5/6・左右腰11/12）から構築した軸並行矩形領域（既存 `build_torso_roi`）。色測定の対象領域。
- **有彩色**: 色相（H）で区別できる、彩度の高い色（ピンク・赤・青など）。
- **無彩色**: 彩度がほぼ0で色相に意味がない色（白・黒・灰）。白＝明度高、黒＝明度低。
- **chroma_ratio**: 胴体ROI内で「彩度 S ≥ sat_min かつ 明度 V ≥ val_min」を満たす画素の割合（既存 `extract_chroma_hsv` が算出、値域 [0.0, 1.0]）。
- **色レジーム**: 提案ロジックの分岐区分。`chromatic`（有彩色）または `achromatic`（無彩色）の2値。chroma_ratio を1つの閾値で判定する。
- **percentile**: レンジ境界を決めるときに使う百分位幅（既存 `--percentile`、デフォルト5.0）。下限を p、上限を 100−p 百分位に取る。

## 3. 機能要求一覧

### FR-001: 色レジームの自動判定

- **機能名**: 色レジーム判定
- **概要**: 胴体ROIの chroma_ratio を1つの閾値で評価し、提案ロジックを `chromatic` / `achromatic` に振り分ける。
- **入力**: 胴体ROI（BGR 画像領域）、chroma_ratio、レジーム判定閾値（CLI 引数、後述 FR-005）。
- **出力**: 色レジーム文字列（`chromatic` または `achromatic`）を stdout に1行表示し、後続の提案ロジックの分岐に使う。
- **判定規則**: `chroma_ratio >= 閾値` なら `chromatic`、`chroma_ratio < 閾値` なら `achromatic`。デフォルト閾値は 0.4（実測根拠は機能設計書 ADR-2）。
- **受け入れ基準**（デフォルト閾値 0.4、`--sat-min`/`--val-min` デフォルト 20/60 で測定）:
  - E0049（白服4枚、chroma_ratio 実測 0.044〜0.247）の胴体ROIで `achromatic` と判定され、stdout に `regime = achromatic` を含む行が表示される。
  - E0014（ピンク服3枚、chroma_ratio 実測 0.713〜0.905）の胴体ROIで `chromatic` と判定され、stdout に `regime = chromatic` を含む行が表示される。

### FR-002: 無彩色レジームのレンジ提案

- **機能名**: 無彩色レンジ提案
- **概要**: `achromatic` と判定された場合、色相 H を全域に開き、彩度 S・明度 V を胴体ROIの全画素分布から percentile で囲んだ服色レンジを提案する。
- **入力**: 胴体ROIの全画素の H/S/V 配列、percentile。
- **出力**: 服色レンジ `[((0, S_lo, V_lo), (179, S_hi, V_hi))]`（1レンジ）。S_lo/S_hi/V_lo/V_hi は全画素 S・V の p / 100−p 百分位（整数）。
- **受け入れ基準**（いずれも `--percentile` デフォルト 5.0 で測定）:
  - E0049（白服4枚）で、提案レンジの S 上限が 80 以下・V 下限が 100 以上（白＝低彩度・高明度を反映）になる。実測値: S 上限 19〜71、V 下限 143〜164。
  - 提案レンジを `compute_ratio_for_ranges` で当てた `proposed_ratio` が 0.7 以上（白服の安定捕捉）。実測値: 0.83〜0.91。
  - 補足: README に記した手作業レンジ `((0,0,150),(179,40,255))`（S下限0/V上限255固定）の比率0.83〜0.98と、本提案レンジ（S/V とも percentile 上下限）の比率0.83〜0.91が近い水準であることを確認済み。0.7 は実測下限0.83に対する安全側の合格ラインとして設定した目標値。

### FR-003: 有彩色レジームの後方互換維持

- **機能名**: 有彩色レンジ提案（既存維持）
- **概要**: `chromatic` と判定された場合、既存の色相クラスタ提案ロジック（`propose_ranges_from_chroma`）を**変更なしで**使う。
- **入力**: 既存と同じ（chroma 画素の H/S/V、percentile）。
- **出力**: 既存と同じ服色レンジ。
- **受け入れ基準**:
  - E0014（ピンク服、単一画像モード）で、改修前と改修後の「提案レンジ・proposed_ratio・出力 JSON ファイル」がバイト一致する（`git stash` 突合）。
  - バイト一致の対象は出力 JSON ファイルと「提案レンジ・proposed_ratio を示す stdout 行」とする。新規に追加する `[INFO] regime = chromatic ...` の1行は後方互換の対象外（増えてよい）。これは判定情報の追加表示でありレンジ提案結果を変えないため。

### FR-004: PNG 可視化の無彩色対応

- **機能名**: 無彩色レジームの診断 PNG
- **概要**: `achromatic` レジームのとき、PNG のヒストグラムパネルに「全画素」の H/S/V 分布を表示し、提案レンジの S/V 境界線を重ねる。`chromatic` のときは既存のクロマ画素ヒストグラム表示を維持する。
- **入力**: 胴体ROI、色レジーム、提案レンジ。
- **出力**: 既存と同じ 2×3 パネルの PNG。`proposed mask` パネルは `achromatic` でも提案レンジで再計算して表示する。
- **受け入れ基準**:
  - E0049（白服）の出力 PNG で `proposed mask` パネルが服領域に白く点灯する（ほぼ黒ではない）。
  - 下段ヒストグラムに「no chroma pixels」ではなく全画素の S/V 分布と境界線が表示される。

### FR-005: レジーム判定閾値の CLI 引数化

- **機能名**: レジーム判定閾値の外部化
- **概要**: FR-001 のレジーム判定に使う chroma_ratio 閾値を CLI 引数で指定可能にする。
- **入力**: CLI 引数（float、値域 [0.0, 1.0]）。
- **出力**: 指定値が FR-001 の判定に使われる。未指定時はデフォルト値 0.4 を使う。
- **受け入れ基準**:
  - E0014_01.png（chroma_ratio≈0.713）に対し、`--chroma-regime-min 0.8` を指定すると `achromatic` と判定され、未指定（デフォルト 0.4）では `chromatic` と判定される。
  - E0049 102543.png（chroma_ratio≈0.247）に対し、`--chroma-regime-min 0.2` を指定すると `chromatic` と判定され、未指定（デフォルト 0.4）では `achromatic` と判定される。

### FR-006: 複数画像モードの色非依存対応

- **機能名**: 複数画像プール提案の色非依存化
- **概要**: 複数画像モード（feat-055）でも、プールした全画像の胴体ROIに対し FR-001 のレジーム判定を行い、`achromatic` ならプールした全画素から FR-002 のレンジを提案する。`chromatic` なら既存のプール提案（クロマ画素プール）を維持する。
- **入力**: 複数の服画像、percentile、レジーム判定閾値、`--threshold`。
- **出力**: 単一の統合服色レンジ（既存と同じ統合 JSON 1個）。各画像の `proposed_ratio` を `--threshold` と照合したレポート（既存仕様どおり、表示のみ・exit 0）。
- **受け入れ基準**:
  - E0049 の白服画像を複数枚渡すと `achromatic` 判定でプールレンジが提案され、各画像の `proposed_ratio` がレポートされる。
  - ピンク服を複数枚渡したときの出力が改修前と一致する（後方互換）。

## 4. 非機能要求

- **パフォーマンス**: 改修による1画像あたりの処理時間増加は無視できる範囲（ROI内のnumpy統計計算の追加のみ。ViTPose 推論が支配的で従来同等）。
- **対応環境**: 既存と同じ（Linux / Python 3.10 / uv / GPU cuda:0）。新規ライブラリ追加なし（numpy / OpenCV / matplotlib のみ）。
- **信頼性**: 画像読み込み失敗・推論失敗時は既存と同じく `[ERROR]` を出して exit 1。提案レンジが空（胴体ROIが空など）のときは `[WARN]` を出して JSON を出力しない（既存仕様を踏襲）。

## 5. 制約条件

- **使用必須**: 既存の ViTPose 推論経路（`merge_halpe26.py`）、`postprocess_pink_id.py` の `compute_pink_ratio` / `FIXED_HSV_RANGES` / `MIN_PINK_RATIO` を再利用する。
- **変更禁止**: `merge_halpe26.py`、`postprocess_pink_id.py` は変更しない。
- **出力形式**: 提案 JSON は `postprocess_pink_id.py --hsv-config` 互換（`fixed_hsv_ranges` + `min_pink_ratio` の2キー、compact 整形）を維持する。
- **後方互換**: 有彩色画像に対する既存の出力（stdout の提案行・PNG・JSON）を変えない。

## 6. 優先順位（MoSCoW）

- **Must**: FR-001, FR-002, FR-003, FR-005（白服でレンジを提案でき、かつ有彩色の後方互換を壊さない＝MVP）
- **Should**: FR-004（診断 PNG の無彩色対応）, FR-006（複数画像モード対応）
- **Could**: なし
- **Won't（今回やらない）**:
  - 白服患者を動画で他人・白い寝具と区別して正しく選べるか（判別力）の検証。これは特徴量を出せることの先の別問題であり、本案件のスコープ外。
  - 「白」「黒」など色名の自動ラベル付け（方式Bは分類しないため出力しない）。

## MVP の範囲

E0049（白服）の単一画像に対し、`achromatic` 判定で白を捕まえるレンジを提案し JSON 出力でき（FR-001/002/005）、かつ E0014（ピンク服）の出力が改修前とバイト一致する（FR-003）こと。
