# docs/BUGFIX_STANDARD.md

## 不具合修正 記述基準
本基準に従って不具合の調査・修正を行うこと。

---

### 適用範囲

以下のケースに本基準を適用する:
- 独立したバグ案件（bug-XXX）
- 開発フロー ステップ7（手動テスト）で発見された不具合
- 既存機能のリグレッション

要求仕様書に該当する記述がない場合（仕様未定義の不具合）は、
不具合修正ではなく**機能追加（feat-XXX）として扱い**、
`REQUIREMENTS_STANDARD.md` と `DESIGN_STANDARD.md` に従って
要求仕様書・機能設計書を作成すること。

---

### 1. 修正計画の必須項目

不具合修正のコード変更前に、以下を `docs/issues/{案件フォルダ}/investigation.md` に記録する。

#### 1.1 不具合の特定
- **対応する要求ID**: どの要求が満たされていないか（例: FR-003）
- **対応する設計セクション**: 機能設計書のどの箇所に関連するか
- **現在の動作**: 何が起きているか（再現手順を含む）
- **期待する動作**: 要求仕様書・機能設計書の該当箇所を引用する
- **エラーメッセージ**: 完全なトレースバックを記録する

#### 1.2 原因分析
- **原因箇所**: ファイル名、関数名、該当コード
- **原因の説明**: なぜこの動作になっているか
- **根本原因 or 表面的原因**: 本当の原因か、症状を抑えているだけかを判断する

#### 1.3 修正内容
- **変更対象ファイル**: ファイル名と変更内容（具体的に）
- **変更しないファイル**: 影響範囲にあるが変更不要な場合、その理由
- **修正コード**: 修正前・修正後のコードを示す
- **修正が設計書に沿っているか**: 設計書と矛盾する修正が必要な場合は明記する

#### 1.4 影響範囲
- **他の機能への影響**: 修正が波及する機能を列挙する
- **リグレッションリスク**: 修正によって壊れる可能性がある箇所

#### 1.5 確認方法
- **テスト項目**: どうテストすれば直ったと言えるか
- **自動テスト**: 自動テストで検証可能か（可能なら `tests/` にテストを追加する）
- **手動テスト**: 実機確認が必要な手順

---

### 2. 記述ルール

#### 2.1 禁止表現（REQUIREMENTS_STANDARD.md と同一）
曖昧表現を使わない。「おそらく」「〜かもしれない」「たぶん」は禁止。
原因が特定できない場合は「原因未特定。仮説: ○○」と明記する。

#### 2.2 設計書との整合性
- 修正は既存の設計書（`design.md`）に沿って行う
- 修正によって設計書の変更が必要になる場合は、**設計書の変更案も併せて提示する**
- 設計書を変更せずにコードだけ変えてはならない

#### 2.3 スコープの限定
- 1つの不具合修正で、報告された不具合以外のコード変更を行わない
- 修正中に別の問題を発見した場合は、別の案件として報告する
- 「ついでにリファクタリング」は禁止

---

### 3. ステップ7（差し戻し）での運用

開発フロー ステップ7 で問題が発見された場合、**修正計画を `investigation.md` に追記し、レビューを経てから修正する**。
本基準は `investigation.md` に何を書くかを定めるものであり、開発フロー自体を短縮・省略するものではない。
繰り返すステップは案件種別で異なる:

- **不具合修正フロー（bug-XXX）**: CLAUDE.md の不具合修正フロー ステップ2〜7 を繰り返す
- **機能追加フロー（feat-XXX）**: CLAUDE.md の機能追加フロー ステップ4〜7 を、問題が見つかったマイルストーンについて繰り返す（`investigation.md` は案件フォルダ直下に1つ。見出しにマイルストーン ID を含める）。問題の原因がロードマップの前提・分割・順序にある場合は、CLAUDE.md「ロードマップの改訂（再計画）」に従う

具体的な流れ（括弧内は bug / feat のステップ番号）:

1. **調査・修正計画（bug: ステップ2 / feat: ステップ4）**: 本基準セクション1に従い、修正計画を `investigation.md` に**追記**する（上書きしない）
   - 日付とイテレーション番号を見出しに含める（例: `## イテレーション2 (YYYY-MM-DD)`。feat ではマイルストーン ID も含める。例: `## イテレーション2 (YYYY-MM-DD, M3)`）
   - 前回の修正計画を踏まえた上で、新たな原因分析を行う
   - 要求仕様書・機能設計書に不備がある場合は、ドキュメントの修正案も作成する
2. **ドキュメント保存（bug: ステップ3 / feat: ステップ4）**: 修正した要求仕様書・機能設計書・investigation.md を保存する
3. **レビュー・修正（bug: ステップ4〜5 / feat: ステップ5）**: CLAUDE.md のレビュールールに従い、`investigation.md` と（変更した場合は）要求仕様書・機能設計書をレビュー対象に含め、Codex の再帰レビューを重要度「高・中」ゼロまで回した後に人（ユーザー）レビューを行う。問題があれば再調査する
4. **実装（bug / feat: ステップ6）**: ユーザーの承認後にコード修正を行う
5. **手動テスト（bug / feat: ステップ7）**: ユーザーが実機で再テストする。問題があれば再び 1 に戻る
